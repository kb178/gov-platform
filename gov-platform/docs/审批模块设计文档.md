## 一、业务背景

政务平台的核心流程是**老百姓提交申请 → 工作人员审批 → 出结果**。

以"办理居住证"为例，完整的办事流程是：

```
老百姓（用户端）                          工作人员（管理端）
    |                                        |
    |  1. 看办事指南（gov-item 提供）           |
    |  2. 填写申请表单                         |
    |  3. 上传申请材料                         |
    |  4. 提交申请 ──────────────────→  5. 窗口受理（核对材料）
    |                                        |
    |                                   6. 科室审核（审查条件）
    |                                        |
    |                                   7. 领导审批（最终决定）
    |                                        |
    |  8. 收到通知（通过/驳回） ←────────  9. 办结
    |                                        |
    |  10. 下载证照（gov-license 提供）         |
```

审批模块要做的事情就是：**管理这个流程从提交到办结的全过程**。

## 二、角色和职责

| 角色 | 来自 | 在审批流程中做什么 |
|------|------|------------------|
| 办事群众（applicant） | sys_user（user_type=1） | 提交申请、查看进度、接收通知 |
| 窗口人员（window） | sys_user（user_type=2, role=window） | 受理申请、核对材料、初审 |
| 科室审核人（reviewer） | sys_user（user_type=2, role=manager） | 审核材料、审查条件 |
| 领导（approver） | sys_user（user_type=2, role=admin） | 最终审批、决定通过或驳回 |

## 三、审批流程设计

### 3.1 标准审批流程

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  提交申请 │───→│ 窗口受理 │───→│ 科室审核 │───→│ 领导审批 │───→│  办结   │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
     │              │              │              │
     │              │              │              │
     ▼              ▼              ▼              ▼
  [保存草稿]     [退回补材料]    [驳回/退回]    [驳回/通过]
```

### 3.2 节点说明

| 节点 | 处理人 | 可执行操作 | 流转规则 |
|------|--------|-----------|---------|
| 提交申请 | 办事群众 | 提交、保存草稿 | 提交后进入窗口受理 |
| 窗口受理 | 窗口人员 | 受理（材料齐全）、退回补材料、不予受理 | 受理 → 科室审核；退回 → 用户补材料重新提交；不予受理 → 驳回 |
| 科室审核 | 科室审核人 | 审核通过、驳回、退回补材料 | 通过 → 领导审批；驳回 → 流程结束 |
| 领导审批 | 领导 | 审批通过、驳回 | 通过 → 办结（触发发证照）；驳回 → 流程结束 |
| 办结 | 系统自动 | — | 流程终态 |

> 撤回不是节点内的操作，是用户对已提交申请（待受理状态）的反向操作。

### 3.3 状态机

申请单（application）的状态流转：

```
                    ┌──────────────┐
                    │  草稿(0)     │ ←── 用户保存草稿
                    └──────┬───────┘
                           │ 提交
                           ▼
                    ┌──────────────┐
              ┌────→│  待受理(1)   │ ←── 已提交，等窗口处理
              │     └──┬───┬───────┘
              │        │   │
              │  受理  │   │ 窗口退回补材料
              │        │   ▼
              │        │ ┌──────────┐
              │        │ │ 退回(3)  │
              │        │ └────┬─────┘
     补材料    │        │      │ 用户补材料重新提交
     重新提交  │        │      │
              └────────┘      │
                              │
              ┌───────────────┘
              │
              ▼
       ┌──────────────┐
       │  审核中(2)   │ ←── 科室审核中
       └──┬──────┬────┘
          │      │
   科室通过│      │ 科室退回补材料 ──→ 退回(3)
          │      │ 科室驳回 ──→ 已驳回(5)
          ▼
       ┌──────────────┐
       │  审批中(4)   │ ←── 领导审批中
       └──┬──────┬────┘
          │      │
   审批通过│      │ 审批驳回
          ▼      ▼
   ┌──────────┐ ┌──────────┐
   │  已通过   │ │  已驳回   │ ←── 终态
   │  (6)     │ │  (5)     │
   └──────────┘ └──────────┘
```

| 状态码 | 状态名 | 说明 |
|--------|--------|------|
| 0 | 草稿 | 用户已保存但未提交 |
| 1 | 待受理 | 已提交，等待窗口受理 |
| 2 | 审核中 | 窗口已受理，科室审核中 |
| 3 | 退回补材料 | 被退回，用户可补材料重新提交 |
| 4 | 审批中 | 科室审核通过，领导审批中 |
| 5 | 已驳回 | 审批不通过（终态） |
| 6 | 已通过 | 审批通过（终态），触发发证照 |

> 状态码连续递增，0-2 是正常流转，3 是异常分支（退回），4-6 是领导审批阶段，5/6 是终态。

## 四、数据库表设计

### 4.1 申请单表（application）

一次办事申请 = 一条记录，是审批模块的核心表。

```sql
CREATE TABLE `application` (
  `application_id` BIGINT NOT NULL COMMENT '申请单ID',
  `application_no` VARCHAR(32) NOT NULL COMMENT '申请编号（业务编号，如：SQ202611190001）',
  `user_id` BIGINT NOT NULL COMMENT '申请人ID（sys_user）',
  `item_id` BIGINT NOT NULL COMMENT '办理事项ID（item_info）',
  `status` TINYINT DEFAULT 0 COMMENT '状态（0草稿 1待受理 2审核中 3退回补材料 4审批中 5已驳回 6已通过）',
  `apply_time` DATETIME DEFAULT NULL COMMENT '提交申请时间',
  `accept_time` DATETIME DEFAULT NULL COMMENT '受理时间',
  `finish_time` DATETIME DEFAULT NULL COMMENT '办结时间',
  `reject_reason` VARCHAR(500) DEFAULT '' COMMENT '驳回原因/退回原因',
  `urgency` TINYINT DEFAULT 0 COMMENT '是否加急（0普通 1加急）',
  `version` INT DEFAULT 0 COMMENT '版本号（乐观锁，防并发操作冲突）',
  `remark` VARCHAR(500) DEFAULT '' COMMENT '备注',
  `create_by` VARCHAR(64) DEFAULT '' COMMENT '创建者',
  `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_by` VARCHAR(64) DEFAULT '' COMMENT '更新者',
  `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `del_flag` TINYINT DEFAULT 0 COMMENT '删除标志（0存在 1删除）',
  PRIMARY KEY (`application_id`),
  UNIQUE KEY `idx_application_no` (`application_no`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_item_id` (`item_id`),
  KEY `idx_status` (`status`),
  KEY `idx_apply_time` (`apply_time`)
) ENGINE=InnoDB COMMENT='申请单表';
```

**申请编号规则**：`SQ + 年月日 + 4位序号`，如 `SQ202611190001`，每天从 0001 开始递增。

### 4.2 申请表单数据表（application_form_data）

用户填写的表单数据，存 JSON 格式（因为每个事项的表单字段不同）。

```sql
CREATE TABLE `application_form_data` (
  `id` BIGINT NOT NULL COMMENT '主键ID',
  `application_id` BIGINT NOT NULL COMMENT '申请单ID',
  `template_id` BIGINT DEFAULT NULL COMMENT '使用的表单模板ID（item_form_template）',
  `form_data` JSON DEFAULT NULL COMMENT '表单数据（JSON，key=字段名，value=用户填写的值）',
  `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `idx_application_id` (`application_id`)
) ENGINE=InnoDB COMMENT='申请表单数据表';
```

**form_data 示例**：
```json
{
  "name": "张三",
  "idCard": "460105199001011234",
  "phone": "13800000001",
  "address": "海口市龙华区xxx路xxx号",
  "reason": "长期居住"
}
```

### 4.3 申请材料表（application_material）

用户提交的材料清单，对照 `item_material_relation` 中配置的必需材料。

```sql
CREATE TABLE `application_material` (
  `id` BIGINT NOT NULL COMMENT '主键ID',
  `application_id` BIGINT NOT NULL COMMENT '申请单ID',
  `material_id` BIGINT NOT NULL COMMENT '材料模板ID（item_material_template）',
  `material_name` VARCHAR(128) NOT NULL COMMENT '材料名称（冗余，防止模板修改影响历史）',
  `required` TINYINT DEFAULT 1 COMMENT '是否必须（0否 1是）',
  `file_url` VARCHAR(500) DEFAULT '' COMMENT '材料文件URL（上传后的地址）',
  `check_status` TINYINT DEFAULT 0 COMMENT '核验状态（0未核验 1通过 2不通过）',
  `check_remark` VARCHAR(255) DEFAULT '' COMMENT '核验备注（如：材料不清晰）',
  `check_by` VARCHAR(64) DEFAULT '' COMMENT '核验人',
  `check_time` DATETIME DEFAULT NULL COMMENT '核验时间',
  `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  KEY `idx_application_id` (`application_id`),
  KEY `idx_material_id` (`material_id`)
) ENGINE=InnoDB COMMENT='申请材料表';
```

**为什么冗余 material_name**：材料模板的名称以后可能会改（比如"身份证"改成"居民身份证"），但历史申请记录里应该保留提交时的名称，不能跟着变。

### 4.4 审批记录表（approval_record）

每一步审批操作都记一条，形成完整的审批痕迹（audit trail）。

```sql
CREATE TABLE `approval_record` (
  `record_id` BIGINT NOT NULL COMMENT '记录ID',
  `application_id` BIGINT NOT NULL COMMENT '申请单ID',
  `node_name` VARCHAR(64) NOT NULL COMMENT '审批节点名称（窗口受理/科室审核/领导审批）',
  `approver_id` BIGINT NOT NULL COMMENT '审批人ID（sys_user）',
  `approver_name` VARCHAR(64) DEFAULT '' COMMENT '审批人姓名（冗余）',
  `action` TINYINT NOT NULL COMMENT '操作（1受理 2通过 3驳回 4退回补材料 5不予受理）',
  `opinion` VARCHAR(500) DEFAULT '' COMMENT '审批意见',
  `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '操作时间',
  PRIMARY KEY (`record_id`),
  KEY `idx_application_id` (`application_id`),
  KEY `idx_approver_id` (`approver_id`)
) ENGINE=InnoDB COMMENT='审批记录表';
```

**审批记录示例**：

| application_id | node_name | approver_name | action | opinion |
|---------------|-----------|---------------|--------|---------|
| 1001 | 窗口受理 | 李四 | 1-受理 | 材料齐全，予以受理 |
| 1001 | 科室审核 | 王五 | 2-通过 | 符合办理条件 |
| 1001 | 领导审批 | 赵六 | 2-通过 | 同意办理 |

## 六、核心业务规则

### 6.1 状态流转控制

```java
// 只允许以下流转：
草稿(0)     → 待受理(1)      // 用户提交
待受理(1)   → 审核中(2)      // 窗口受理
待受理(1)   → 退回(3)        // 窗口退回补材料
待受理(1)   → 已驳回(5)      // 不予受理（窗口人员判定不符合受理条件）
待受理(1)   → 草稿(0)        // 用户撤回（回到草稿，可修改后重新提交）
审核中(2)   → 审批中(4)      // 科室审核通过
审核中(2)   → 已驳回(5)      // 科室驳回
审核中(2)   → 退回(3)        // 科室退回补材料
审批中(4)   → 已通过(6)      // 领导审批通过
审批中(4)   → 已驳回(5)      // 领导驳回
退回(3)     → 待受理(1)      // 用户补材料重新提交
```

> "撤回"是用户在申请被受理之前主动取消，回到草稿状态，可以修改后重新提交，不会产生审批记录。

### 6.2 操作权限控制

| 操作 | 允许的角色 | 前置状态 | 说明 |
|------|-----------|---------|------|
| 提交申请 | 办事群众 | — | |
| 保存草稿 | 办事群众 | — | |
| 修改草稿 | 申请人本人 | 草稿 | |
| 删除草稿 | 申请人本人 | 草稿 | |
| 撤回申请 | 申请人本人 | 待受理 | 回到草稿，不产生审批记录 |
| 受理 | 窗口人员 | 待受理 | 材料齐全，进入审核 |
| 不予受理 | 窗口人员 | 待受理 | 材料/条件不符合，直接驳回 |
| 审核通过 | 科室审核人 | 审核中 | |
| 审批通过 | 领导 | 审批中 | |
| 驳回 | 科室/领导 | 审核中/审批中 | 审核不通过，流程结束 |
| 退回补材料 | 窗口/科室 | 待受理/审核中 | 不是拒绝，是让用户补材料再提交 |
| 重新提交 | 申请人本人 | 退回补材料 | |

**"不予受理"和"驳回"的区别**：
- **不予受理**：窗口人员在受理阶段判定不符合受理条件（比如不属于本部门管辖、材料明显不全），直接拒绝，不进入审核流程
- **驳回**：科室/领导在审核/审批阶段判定不符合办理条件，是业务层面的拒绝

两者最终状态都是"已驳回(5)"，但在 `approval_record` 中的 action 码不同（不予受理=5，驳回=3），审批记录里能区分。

### 6.3 材料完整性校验

提交申请时：
1. 查询该事项配置的材料清单（`item_material_relation` 中 `required=1` 的）
2. 校验用户是否上传了所有必需材料
3. 缺少必需材料 → 不允许提交，提示缺少哪些

### 6.4 办结后续动作

审批通过（状态变为"已通过"）时：
1. 记录办结时间
2. **发消息通知**（调 gov-message）
3. **生成证照**（调 gov-license）
4. 记录审批日志

### 6.5 防重复审批

同一个申请可能被多个工作人员同时看到（比如待办列表里都有），要防止两个人同时操作同一个申请：

**方案：数据库乐观锁 + Redis 分布式锁**

```java
// 1. Redis 分布式锁（同一申请同一时间只能一个人操作）
String lockKey = "approval:lock:" + applicationId;
boolean locked = redisUtils.setIfAbsent(lockKey, userId, 30, TimeUnit.SECONDS);
if (!locked) {
    throw new BusinessException("该申请正在被其他人处理，请稍后再试");
}

// 2. 数据库乐观锁（双重保障）
// application 表加 version 字段，更新时带上旧版本号
UPDATE application SET status = ?, version = version + 1
WHERE application_id = ? AND version = ? AND status = ?
// 影响行数为 0 → 说明已经被别人改了 → 提示"操作失败，请刷新后重试"
```

操作完成后释放 Redis 锁。

## 七、技术方案

### 7.1 Flowable 工作流引擎

**为什么用 Flowable**：
- 审批流程是典型的"工作流"场景：有节点、有流转规则、有审批人分配
- 自己写状态机可以做，但流程变更（比如加一个审批节点）就要改代码
- Flowable 用 BPMN 流程图来定义流程，改流程只需要改配置

**BPMN 流程图**（对应上面的标准审批流程）：

```
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ 开始事件 │──→│用户任务1 │──→│用户任务2 │──→│用户任务3 │──→│ 结束事件 │
│         │   │ 窗口受理 │   │ 科室审核 │   │ 领导审批 │   │         │
└─────────┘   └─────────┘   └─────────┘   └─────────┘   └─────────┘
                   │              │              │
                   │              │              │
                   ▼              ▼              ▼
               [退回/驳回]    [退回/驳回]     [驳回]
```

**Flowable 核心概念**：

| 概念 | 说明 | 对应到我们的业务 |
|------|------|----------------|
| ProcessDefinition | 流程定义（BPMN 图） | "居住证办理流程" |
| ProcessInstance | 流程实例（一次运行） | 张三的一次申请 |
| Task | 用户任务（待办） | 窗口人员的待受理任务 |
| HistoricTask | 历史任务 | 已完成的审批记录 |
| Variable | 流程变量 | 申请ID、当前审批人、审批结果 |

**但也可以不用 Flowable**：如果觉得 Flowable 太重，自己写状态机也行。核心就是上面那张状态流转图，用 if/else 或状态模式实现。面试时说"我用状态机实现了审批流转，如果流程更复杂可以接入 Flowable"也完全可以。

### 7.2 技术选型

| 组件 | 选择 | 用途 |
|------|------|------|
| 流程引擎 | Flowable 7.x（或自研状态机） | 管理流程节点和流转 |
| 文件上传 | MinIO | 存储申请材料文件 |
| 消息通知 | RabbitMQ + gov-message | 审批结果通知 |
| 生成证照 | iText / wkhtmltopdf | 审批通过后生成 PDF 证照 |
| 定时任务 | Spring Scheduler | 超时提醒、超时自动处理 |

## 八、与外部服务的交互

```
gov-approval（审批服务）
    │
    ├──→ gov-system（用户服务）
    │    通过 Feign 查询审批人信息、用户角色
    │
    ├──→ gov-item（事项服务）
    │    通过 Feign 查询事项详情、表单模板、材料配置
    │
    ├──→ gov-message（消息服务）
    │    审批通过/驳回后，调用发送通知
    │
    ├──→ gov-license（证照服务）
    │    审批通过后，调用生成证照
    │
    └──→ Redis
         缓存待办列表、分布式锁（防重复审批）
```
